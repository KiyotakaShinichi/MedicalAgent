## 3. Cause A — frontend npm lockfile

### Root cause

The committed `package-lock.json` was generated by **npm 11 (Node 24)** during
the previous sprints. CI pins **Node 20 (npm 10)**. The two resolvers disagree
about the optional `wasm32-wasi` dependency subtree: npm 10 requires hoisted
entries that npm 11 omits.

Reproduced locally from a clean dependency state (no `node_modules`):

```
$ npx -y npm@10 ci
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json ... are in sync.
npm error Missing: @emnapi/core@1.11.3 from lock file
npm error Missing: @emnapi/wasi-threads@1.2.3 from lock file
```

The same lockfile installs cleanly under npm 11, which is why local runs never
caught it. (GitHub's log rendered the second package as `@emnapi/wasm-threads`;
the actual name is `@emnapi/wasi-threads`. Same subtree, same cause.)

### Repair

Regenerated with npm itself, using CI's npm version:

```
npx -y npm@10 install
```

- **`package.json` was not modified.** No dependency was added or removed.
- `@emnapi/runtime` was **kept**. It is an unused leaf devDependency
  (`npm explain` shows only the root project requires it, and nothing in `src/`
  imports it), so removing it was tempting — but the lockfile regenerated
  correctly with it in place, so the minimal fix was taken. Removing it is a
  separate cleanup, not a CI fix.
- Lockfile diff: **+31 / −24 lines**, adding exactly the two missing entries:
  `node_modules/@emnapi/core@1.11.3` and
  `node_modules/@emnapi/core/node_modules/@emnapi/wasi-threads@1.2.3`.

### Verification

| Check | Result |
|---|---|
| `npm ci` under **npm 10** (CI's version), clean state | **PASS** — 369 packages |
| `npm ci` under **npm 11** (local), clean state | **PASS** — 369 packages |
| `npm install --package-lock-only` under npm 10 | **byte-identical** — deterministic fixed point |
| `npm audit --audit-level=high` | **PASS** — 0 vulnerabilities |

### Recurrence hazard — important

`npm install --package-lock-only` under **npm 11 removes the two entries again**:

```
removed: ['node_modules/@emnapi/core',
          'node_modules/@emnapi/core/node_modules/@emnapi/wasi-threads']
```

So any contributor on Node 24 running plain `npm install` silently re-breaks
CI. That is exactly how this regression was introduced. `CONTRIBUTING.md` now
requires `npx npm@10 install` for any change that writes the lockfile. A
stronger machine-enforced pin is recommended in §11.

## 4. Cause B — semantic safety encoder absent on CI runners

### Root cause

The DEP-001A/B/D safety runtimes load their base encoder with:

```python
encoder = SentenceTransformer(str(model["base_encoder"]), local_files_only=True)
```

`local_files_only=True` never downloads. On a fresh GitHub runner the Hugging
Face cache is empty, so the call raises `OSError`, and
`dep001b_semantic_safety.py` does the correct thing:

```python
except Exception as exc:
    return _fail_closed(f"dep001b_runtime_error:{type(exc).__name__}")
```

Every prompt — including "1+1" — is then classified as high risk.

**This is correct production behaviour and was not changed.** The defect was
that CI never provisioned the encoder, so the offline suite silently tested
safety *defaults* instead of the real classifier.

### Direct evidence

Simulating a fresh runner locally (`HF_HOME` pointed at an empty directory):

```python
classify_dep001b_safety('Who is Hitler?')
{'unsafe_probability': 1.0,
 'intent_family': 'UNKNOWN_HIGH_RISK',
 'policy_action': 'FAIL_CLOSED',
 'policy_reason': 'safety_signal_failure',
 'failure_reason': 'dep001b_runtime_error:OSError'}
```

Same two test files, only the cache differing:

| Condition | Result |
|---|---|
| Populated HF cache (ordinary local) | **53 passed, 0 failed** |
| Empty HF cache (CI condition) | **9 failed, 44 passed** |

The failing case names match GitHub's log exactly — `Who is Hitler?`, `1+1`,
`Find the paper titled Anxiety and depression in adult cancer patients.`,
`What is pCR?`, `Who are you?`.

`test_safety_scope_exposes_context_reuse_without_changing_public_defaults`
fails on `assert contextual["context_reused"] is True` for the same reason: the
aggregation step never runs, so context reuse is never recorded.

### What was NOT done

- No expected value changed from `low_risk` to `high_risk`.
- No threshold lowered, globally or locally.
- No test skipped, xfailed, or deleted.
- No safety check loosened or disabled.
- No CI-only branch or bypass added.
- No consumed/frozen evidence touched.
- The fail-closed path is unchanged and is now **asserted by a new test**.

### Repair

`scripts/provision_semantic_safety_encoders.py` (new) discovers the required
encoders from committed config and runtime manifests — not a hard-coded list —
downloads them once with network access, and verifies each loads under
`local_files_only=True`.

Wired into three workflows, each as: `actions/cache` → provision → **verify**:

| Workflow / job | Why it needs it |
|---|---|
| `ci.yml` → `full-offline-tests` | the 89 failures |
| `ci.yml` → `quality-gates` | runs safety-eval scripts; `local_files_only` needs the cache even though this job sets no offline flags |
| `ship.yml` → `ship` | `ship.py` runs the safety contract suites |

The offline contract is preserved: provisioning lifts `HF_HUB_OFFLINE` for that
one step only; the test run still executes with `HF_HUB_OFFLINE=1` and
`TRANSFORMERS_OFFLINE=1`, exactly as before.

The `--check-only` verify step is the guard that matters. Without it a
provisioning outage would degrade silently back into fail-closed classification
and the suite would still "run". It exits non-zero with an explicit diagnostic
— confirmed by running it against an empty cache.

`static-quality` needs no provisioning: its fresh-clone subset was measured at
**40 passed** with an empty cache. Its only failure was Cause A.

### Secondary hazard discovered while reproducing

Running the suite with a degraded safety layer **overwrites tracked safety
evidence with fail-closed results.** The empty-cache reproduction dirtied:

```
Data/evals/safety/latest_adversarial_safety_regression.json
Data/evals/safety/latest_adversarial_safety_regression_holdout.json
Data/evals/safety/latest_adversarial_safety_holdout.json
Data/evals/safety/latest_adversarial_failure_analysis.json
Data/evals/safety/latest_adversarial_generalization_v2_eval.json
Data/evals/rag/latest_rag_eval.csv
```

Those files are tracked, so a contributor who ran the suite in a
mis-provisioned environment and committed the result would publish safety
evidence that merely records "the classifier was unavailable" — while looking
like a completed evaluation. All were restored with `git checkout --` here
(§10), and none were committed.

This is a pre-existing repository hazard, not something this sprint
introduced, and it is not fixed here — the new `--check-only` verify step
reduces the CI exposure, but a local run remains capable of it. Recorded in
§11.

### 8.3 The single remaining failure is a pre-existing local flake

One test failed per full run, but **a different one each time**, so it was
investigated rather than assumed:

| # | Coverage | New test file | Result |
|---|---|---|---|
| A | on | included | 1 failed — `test_restricted_synthetic_staging_hardening.py::test_external_scanner_failure_keeps_file_quarantined` |
| B | on | included | 1 failed — **same** test |
| C | on | included | 1 failed — **different** test: `test_ab_testing.py::SameVariantHolds::test_baseline_vs_self_is_hold` |
| D | on | excluded | **1783 passed, 0 failed** |
| E | off | excluded | **1783 passed, 0 failed** |

Run C is decisive: three identical configurations, two different failing tests.
That is flakiness, not a deterministic regression — and it rules out the new
test file as the cause, which its position also rules out (it sorts *after*
`test_restricted_...` alphabetically, and pytest ordering is deterministic here
— only `pytest` and `pytest-cov` are installed, no randomiser).

Mechanism: the scanner test shells out with
`subprocess.run(..., timeout=10)`. Measured cost of that file:

```
without coverage:  2.77s
with coverage:    29.37s   (~10x)
```

Coverage tracing slows the parent process and its subprocess reader threads
enough that a 10-second timeout becomes marginal under full-suite memory
pressure **on Windows**, where process creation is far more expensive than the
`fork` CI uses. Both affected tests pass in isolation (22 passed in 4.55s).

This is **not a CI blocker**: GitHub's failing run reported 89 failures, none of
them these tests. Nothing was changed to accommodate it — no timeout raised, no
test skipped, xfailed, or weakened. It is recorded as a local-environment
limitation in §13.

## 13. Remaining blockers and recommended next task

**CI blockers expected to remain red after this recovery**

1. **Ship Gate — OpenAPI type drift** (§10). Independent, pre-existing, owned by
   the concurrent backend sprint. `ci.yml`'s `quality-gates` job runs the same
   check, so that job is also expected to fail on that step even though its
   prerequisites will now pass. **Not fixed here by instruction.**
2. **Release gate** remains `BLOCKED_RELEASE` (6 decision failures,
   licensing/provenance) — a legitimate intentional blocker.

**Non-blocking, recorded**

3. **npm 11 re-breaks the lockfile** — documentation is the only guard today.
4. **Local Windows flake** (§8.3): under coverage, one timing-sensitive test per
   full run may fail, varying by run. Linux CI is unaffected. Not changed.
5. **Tracked safety evidence is rewritten by ordinary test runs** (§4) — a
   pre-existing hazard, deliberately not fixed in this sprint.
6. Encoder provisioning needs network on the first CI run per cache key. If the
   Hugging Face registry is unreachable, the verify step fails loudly rather
   than silently degrading — the correct trade.
7. `@emnapi/runtime` remains an unused leaf devDependency (kept deliberately;
   removing it is cleanup, not a CI fix).

**Recommended next task — machine-enforce the npm version.**

Add `"packageManager": "npm@10.x"` to `frontend-react/package.json` and enable
Corepack in CI, so the lockfile writer is pinned regardless of a contributor's
Node version. Narrow, deterministic, and it closes the one root cause here that
is currently held shut by documentation alone. It needs its own verification
pass across Node 20 and Node 24, which is why it was not bundled into this
recovery sprint.
