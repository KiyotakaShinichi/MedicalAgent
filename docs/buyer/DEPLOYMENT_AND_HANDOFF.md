# Deployment, database, and operations handoff

## Local synthetic demo

```bash
uv sync --frozen --all-groups
python scripts/bootstrap.py
uv run python scripts/seed_buyer_demo.py
uv run uvicorn backend.api.main:app --host 127.0.0.1 --port 8017
cd frontend-react && npm ci && npm run dev -- --host 127.0.0.1
```

Open `http://127.0.0.1:5173`. The core walkthrough needs no cloud/provider key.
The separate buyer demo database is under `Data/test_tmp/buyer_demo/` and is
clearly marked synthetic.

## Database lifecycle

- **Initialize/migrate:** `DATABASE_URL=... python -m alembic upgrade head`
- **Seed buyer demo:** `uv run python scripts/seed_buyer_demo.py`
- **Reset buyer demo:** `uv run python scripts/reset_buyer_demo.py`
- **Backup:** `uv run python scripts/buyer_demo_database.py backup --output Data/test_tmp/buyer_demo/backup.sqlite`
- **Restore:** `uv run python scripts/buyer_demo_database.py restore --backup Data/test_tmp/buyer_demo/backup.sqlite`
- **General local reset:** `python scripts/reset_local_db.py` (SQLite only)

Buyer-demo reset/restore refuses paths outside its disposable root and refuses
unmarked databases. Backup uses SQLite's online backup API. This is a local
handoff aid, not enterprise disaster recovery. A hosted owner must define and
exercise PostgreSQL backup/restore, encryption, RPO/RTO, retention, and disaster
recovery.

## Production-shaped synthetic profile

`docker compose -f docker-compose.prod.yml up --build` requires a database
password and defaults to staging/synthetic boundaries, disabled demo auth,
shared rate limiting, PostgreSQL, Redis, and fail-closed dense RAG requirements.
It remains a staging shape, not proof of public or clinical production. Add a
real IdP, TLS/reverse proxy, secret manager, durable object storage, centralized
telemetry, error reporting, backup/restore, vulnerability response, and operator
ownership before hosting.

## Operator runbook

1. Copy `.env.example` to an untracked secret source and set the minimum profile.
2. Verify dependency locks and run `python scripts/verify_buyer_candidate.py`.
3. Provision derived KB/index artifacts with `python scripts/bootstrap.py` or the
   documented offline provisioning path.
4. Apply migrations before starting API/workers.
5. Start database/cache, API, worker, then frontend.
6. Check `/health` for liveness and `/ready` for dependency-aware readiness.
7. Use structured logs and `X-Request-ID` to correlate errors. Logs are redacted,
   but deployment retention/access remains the operator's responsibility.
8. On provider failure, keep optional services disabled or use offline/local
   behavior; never weaken safety because retrieval/provider calls fail.
9. On evidence/regression failure, follow `docs/runbooks/`; do not edit artifacts
   or thresholds to make gates green.
10. Stop services gracefully, then back up managed state according to policy.

## Common failures

- **Empty RAG index:** run declared derived-artifact provisioning from tracked KB
  inputs; do not commit generated indexes.
- **Demo login rejected:** confirm development environment or explicit demo-auth
  allowance; never enable demo credentials in a hosted production profile.
- **Readiness degraded:** inspect the component list and request ID; `/health`
  alone does not prove dependencies are ready.
- **Provider timeout:** verify buyer-owned endpoint/key/budget and keep the core
  safety path fail closed.
- **Migration error:** stop startup, back up state, inspect Alembic revision, and
  test on a copy. Do not rely on ad hoc schema patches for hosted upgrades.
- **Evidence gate failure:** preserve the result and follow the relevant runbook.

## Dependency upgrades

Update lockfiles through the documented package managers, run dependency and
vulnerability checks, then the complete backend/frontend/evidence gates. Never
upgrade model/provider behavior silently or overwrite evidence generated by a
different implementation revision.
